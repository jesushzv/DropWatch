| 2026-09-01 | The app's database is the Supabase project **`jesushzv's Project`** (`gqezqgasuqqpnqiljsig`), not `business-helper` and not a new project | Founder chose a dedicated project, but the free tier caps the account at 2 active projects and both slots were taken. | 2026-09-01 | **RLS enforcement model (ADR-2 detail):** the app connects as the non-owner role `dropwatch_app`; every query runs in a transaction that sets `app.user_id` / `app.open_id` / `app.role='service'`, and policies read those claims. Migrations carry the policies (`app/drizzle/0001_rls_policies.sql`) | A Drizzle app connecting as the table owner would make RLS decorative — policies exist but never fire. The brief's `USING (user_id = auth.uid())` also cannot work directly: `users.id` is an integer while `auth.uid()` is a UUID. With claims-based policies the database itself refuses cross-tenant access (proven by `rls.integration.test.ts`, which runs in CI), and `watchEvents` has no UPDATE/DELETE grant at all, making the audit trail immutable at the database | The app ever serves data through PostgREST/supabase-js directly — then policies need `auth.uid()`-based variants for those roles |
| 2026-09-01 | **Session model (ADR-3 detail):** keep the first-party HS256 session cookie; Supabase Auth is only the login path. `users.openId` holds the Supabase auth user UUID, exchanged for our cookie at `POST /api/auth/session` | Minimal churn (all session machinery and its tests survive), no Supabase dependency on the request path, and log-in method changes (adding Google, etc.) never touch the app's session handling. Magic link uses the implicit flow because the link may open in a different browser than the one holding a PKCE verifier | Refresh-token-grade session revocation is ever needed — then verify Supabase tokens per-request instead of minting a year-long cookie |
| 2026-09-01 | The app deploys from its **own** Vercel project, `dropwatch-app` (`prj_I8YvLVlj4BL8GPFWliTzqaq65xjR`), Root Directory `app/`, config in `app/vercel.json`; the repo-root `dropwatch` project is untouched | ADR-5. The 2026-08-29 near-miss was the app trying to live in the probe's project; a separate project with a scoped root directory makes that class of accident structurally impossible. | 2026-09-01 | **Scheduling model (ADR-5 detail):** one platform cron (Vercel Cron, 6-hourly, CRON_SECRET-authenticated) runs every enabled `priceImportSchedules` row; per-user vendor cron registration (Manus heartbeat) is deleted | The heartbeat client was the last Manus call on a product path. A single cron over a schedules table is boring and testable; enable/disable become pure DB toggles. `scheduleCronTaskUid` stays as a vestigial nullable column rather than churning the schema | A user ever needs a custom cadence — then per-row cron expressions start meaning something again |
